# AGENTS.md

Guidance for AI coding agents adding languages to this repository.

## Golden rule

Every implementation must produce **byte-for-byte identical stdout** for the
same stdin. `tests/expected/` holds the authoritative golden output. If you
change the protocol, update `README.md` **and** regenerate the goldens with
`python tests/run_tests.py --update`, then re-run the suite.

## File style

* **No comments at the top of implementation files.** A file under
  `languages/` must start directly with code — no header comment block,
  banner, docstring, or shebang. Keep comments inline beside the code they
  explain, and keep build/run instructions in `README.md` and
  `tests/run_tests.py`, not in the source. (`languages/<id>/README.md` and
  `languages/<id>/banner.svg` are generated documentation, not implementation
  files: they are written by `tools/generate_language_readmes.py`, so never
  hand-edit them. A `frameworks/<id>/banner.svg` is generated by that same
  script too — see **Banners are mandatory** below.)
* **Indent with 4 spaces per level.** Never use tab characters, and step
  continuation lines by 4 spaces as well. (This overrides a language's usual
  convention, e.g. Go's tabs or 2-space JavaScript.)

## What stays untracked

`.gitignore` is the single source of truth for this, and its sections are
deliberate: build output (`tests/build/`, `dist/`, `build/`, `target/`,
`**/obj/`), tool caches (`.gradle/`, `.kotlin/`, `node_modules/`, `__pycache__/`),
the generated showcase data (`public/dashboard-data.js`) and editor cruft. Two
consequences worth remembering:

* A Gradle run rewrites `frameworks/*/.gradle/`, `frameworks/*/build/` and
  `.kotlin/` by itself, so those files are ignored **and** untracked — never
  `git add` one back in (a committed file is not affected by `.gitignore`, which
  is how 50 of them once kept showing up as changes).
* Likewise never commit a compiled program, a capture, or `dist/`: everything in
  those directories is regenerated by the suite, `npm run data` or CI.

## Workflow when adding a language

1. Pick a language and confirm its toolchain (see the auto-install section
   below). If it is missing, **install it automatically** instead of asking.
2. Create `languages/<name>/connect_four.<ext>` implementing the console
   protocol documented in `README.md` exactly. Start the file directly with
   code — no top-of-file comments (see **File style**).
3. Register it in the `LANGUAGES` list in `tests/run_tests.py`:
   * `name`   - short id, matching `languages/<name>/`
   * `source` - path to the source file
   * `build`  - argv that compiles/prepares it, or `None`
   * `run`    - argv that runs it
   * also add a `build` output path under `tests/build/` (git-ignored).
4. Run `python tests/run_tests.py`. Every scenario must pass and every
   language must agree. Fix the new implementation, never the goldens.
5. Add the language to the table in `README.md`, to the install table below, and
   its badge to the wall at the top of that README (see **The badge wall**).
6. Refresh the static showcase: `npm run data` (it runs
   `tools/generate_dashboard.py` for you, and CI runs the same generator on every
   push).
7. Refresh the folder's docs: add a display entry to `LANGUAGE_INFO` in
   `tools/generate_dashboard.py` (name, Prism class, category) and a facts entry
   to `INFO` in `tools/generate_language_readmes.py`, then run
   `python tools/generate_language_readmes.py`. It writes
   `languages/<name>/README.md` (prerequisites, install commands, how to build
   and play) and `languages/<name>/banner.svg` (the skills banner at the top of
   that README). It cross-checks the tool names, artifacts and source paths it
   documents against the runner and prints a warning when they drift, so a
   command the runner changed must be updated here too.

### Non-console languages (the HTML/CSS exception)

`languages/` is for programs the master suite can feed stdin and diff stdout.
The single exception is **HTML/CSS** (`languages/htmlcss/`): a browser page
cannot read stdin or print the golden stdout, so it is deliberately **not** in
`LANGUAGES` in `tests/run_tests.py`. Wire another one up the same way:

* display metadata in `LANGUAGE_INFO` in `tools/generate_dashboard.py`
  (name, Prism class, category);
* an entry in `INTERACTIVE_LANGUAGES` there for its `note`/`linkText` banner and
  the `preview` path the dashboard loads in its **Play** tab (an iframe) - which
  is why the dashboard needs no page-side change to add another. The one thing to
  check is the build: a preview page that does not live under
  `languages/htmlcss/` has to be copied into `dist/` by the plugin in
  `vite.config.ts`, which the dev server does not need; and
* `"interactive": True` in `INFO` in `tools/generate_language_readmes.py`, which
  skips the runner cross-check and writes a README that explains the omission.

Keep the byte-for-byte guarantee for everything that *is* a console program.

## Banners are mandatory

**Every folder under `languages/` and `frameworks/` ships a `banner.svg`**, and
it is generated — never hand-written, never hand-edited, never skipped.
`tools/generate_language_readmes.py` writes both:

* a language's banner from its `INFO` entry (`toolchain` + `skills`),
* a framework's banner from its `FRAMEWORK_BANNERS` entry (`toolchain` +
  `skills`),

using the same `banner_svg()` and the dashboard's navy/mint palette, so a
language and a framework look like the same project card. A new language or
framework is not finished until its banner exists and the README opens with
`<img src="banner.svg" ...>`.

## The badge wall

The top of the top-level `README.md` is a wall of **[shields.io](https://shields.io)**
badges — one per folder, languages first and then frameworks — rather than a
generated image, so it renders everywhere and stays a line or two to extend. Add
the badge next to the others:

```markdown
![Python](https://img.shields.io/badge/Python-3776AB?style=for-the-badge&logo=python&logoColor=white)
```

* `style=for-the-badge` is the tall one the wall uses; it sets the text in caps.
* Every badge is **clickable**, wrapped in a link to the folder it names:

  ```markdown
  [![Vue](https://img.shields.io/badge/Vue-4FC08D?style=for-the-badge&logo=vuedotjs&logoColor=black)](https://github.com/pattygcoding/Neo-Connect-Four-Language-Tree/tree/main/frameworks/vue)
  ```

  The target is `<repository>/tree/<branch>/<folder>` — the same shape the
  dashboard's header link builds — so the badge and the panel it points at agree
  about where the code lives.
* The colour is the brand's own hex, and `logo=` is resolved against
  [simple-icons](https://simpleicons.org) — so a slug that exists there is a slug
  that renders here. **Look at the badge before committing it:** an unknown slug
  still answers 200, just without the mark.
* `logoColor` is `white`, or `black` on a pale brand (JavaScript's yellow, React's
  cyan) — the same choice shields makes for the text beside it.
* Escape the name: `-` becomes `--`, a space becomes `_`, and `#`, `+`, `(`, `)`
  become `%23`, `%2B`, `%28`, `%29`. So `Objective-C` is `Objective--C`, `C#` is
  `C%23`, `F#` is `F%23`, `C++` is `C%2B%2B` and `Tiger (Custom)` is
  `Tiger_%28Custom%29`.
* A project with no icon of its own (Ada, COBOL, PowerShell, Prolog, Assembly,
  Objective-C, Tiger, Firebird, Db2, Oracle, QuestDB, T-SQL, Playwright) keeps its
  badge and just drops `logo=`, with a colour of its own. For a brand that has an
  icon but no colour to hand, `https://cdn.simpleicons.org/<slug>` serves the SVG
  whose `fill` is that colour.

## Workflow when adding a framework

Frameworks (.NET MAUI, Ruby on Rails, Django, Express, FastAPI, Fastify, Fiber, Flask, Flutter, Gin, Laravel, NestJS, Next.js, Nuxt, Phoenix, React, React Native, Angular, Vue, Svelte, Symfony, Spring Boot, Blazor, ASP.NET Core, and more) are **not**
console programs, so they live in `frameworks/<id>/` rather than
`languages/<id>/` and stay outside the byte-for-byte suite. The dashboard still
renders them, one representative file at a time.

1. Create `frameworks/<id>/` with the real project files (model, controller,
   views, routes, ...). A framework app serves HTML, so it does **not** need to
   match the console protocol, and it is **not** added to `LANGUAGES` in
   `tests/run_tests.py`.
2. Describe it in `FRAMEWORK_INFO` in `tools/generate_dashboard.py`: `name`,
   `prism` (the Prism grammar class), `category`, the representative `file`
   (relative to the framework folder), the `folder` linked on GitHub, and the
   `note`/`linkText` banner. Put a `{link}` placeholder in `note` where the
   "view the whole project" anchor is injected - a framework app is many files,
   so the note explains that the panel shows one of them.
3. Write `frameworks/<id>/README.md` by hand (the language README generator is
   language-specific): prerequisites, how to run it, and the skills it shows.
   Open it with the banner image: `<img src="banner.svg" ...>`.
4. Add a facts entry to `FRAMEWORK_BANNERS` in
   `tools/generate_language_readmes.py` (`toolchain` + `skills`) and run
   `python tools/generate_language_readmes.py` to write
   `frameworks/<id>/banner.svg`. **Do not skip the banner** (see **Banners are
   mandatory** above).
5. Run `npm run data` (or `python tools/generate_dashboard.py`) and add a row to
   the Frameworks table in `README.md` and a badge to the wall at the top of it
   (see **The badge wall** above).

The dashboard reads both lists through one accessor (`modeItems`/`allItems`),
so a new framework needs **no** app change: it appears under the
**Frameworks** pill, deep-links at `/<id>`, shows the `note` banner (with the
GitHub link) above its code, and hides the console-capture tab.

## Automatically installing a missing toolchain

Before building or running a language, check whether its compiler or
interpreter is available. If it is not, install it **without prompting**,
using the first available package manager for the platform, then re-check.
Only edit files and run the tests after the toolchain is present.

Detect (cross-platform, POSIX shell):

```sh
command -v gcc  || install gcc
command -v go   || install go
```

Detect (Windows PowerShell):

```powershell
if (-not (Get-Command gcc -ErrorAction SilentlyContinue)) { winget install -e --id <id> }
```

Notes:

* Use non-interactive installs. On Windows prefer `winget`; fall back to
  `scoop` or `choco`. On Linux prefer `apt-get install -y`; otherwise `dnf`
  or `pacman -S --noconfirm`.
* After installing, open a new shell (or refresh `PATH`) and re-run the
  detection command before building.
* Compilers without a package on some managers: for C on Windows, MSYS2
  (`pacman -S --noconfirm mingw-w64-ucrt-x86_64-gcc`) is a reliable fallback.
* SWI-Prolog's silent installer does not always add `swipl` to `PATH`; if it
  is missing, append its `bin` directory (e.g. `C:\Program Files\swipl\bin`)
  to the user `PATH`.
* GnuCOBOL on Windows (e.g. the Chocolatey package) ships its own older MinGW.
  Put that toolchain's `bin` first on `PATH` (and set `COB_CONFIG_DIR`,
  `COB_CFLAGS`, `COB_LDFLAGS`, `COB_LIBRARY_PATH`) when building, or its C
  backend fails against a different system `gcc`. The `cobol` entry in
  `tests/run_tests.py` does this automatically via its `env`.
* VB.NET and F# both compile with the .NET SDK, so the `vb` and `fsharp`
  entries need no toolchain beyond `dotnet` (same install as C#). Each keeps a
  `ConnectFour.vbproj` / `ConnectFour.fsproj` next to its source.
* The `assembly` entry is win64 assembly in GNU `as` syntax, so it reuses the C
  toolchain (`gcc` assembles and links it in one step). It must be the x86-64
  MinGW-w64 `gcc`, not the 32-bit one that ships with GnuCOBOL; the
  `tests/run_tests.py` entry selects it via `mingw64_env()`.
* Nim compiles through a C compiler, so it needs that same x86-64 `gcc`; the
  `nim` entry also selects it with `mingw64_env()`. Its `--nimcache` is pointed
  into `tests/build` so no cache directory appears next to the source.
* Zig brings its own LLVM backend, but on Windows `zig build-exe` writes the
  `--name` verbatim (it rejects a `.exe` in `-femit-bin`), so the `zig` entry
  runs with `cwd=tests/build` and `--name connect_four_zig` to land
  `connect_four_zig.exe` where the runner expects it.
* Windows has no first-party Objective-C runtime, so the `objectivec` entry
  uses MSYS2's `clang64` environment: clang plus the GNUstep libobjc2 runtime
  (`clang -fobjc-runtime=gnustep-2.0 ... -lobjc`). That `bin` directory must be
  on `PATH` for the build *and* for running the program, because libobjc2 ships
  as `libobjc-4.6.dll` (a compatibility name it keeps from GCC's runtime); the
  entry does this with `msys2_clang_env()`.
* libobjc2 root classes must declare the `isa` ivar explicitly (as GNUstep's
  `NSObject` does) and carry `__attribute__((objc_root_class))`. Without the
  ivar clang computes an instance size that excludes the isa pointer, and
  `class_createInstance()` then returns `NULL`, so every message send yields
  nil.
* Swift builds with `swiftc` from the toolchain installed under
  `%LOCALAPPDATA%\Programs\Swift`. The `swift` entry's `swift_env()` supplies
  the three things `swiftc` needs: `SDKROOT` pointing at the toolchain's own
  `Windows.sdk`, the MSVC environment captured from `vcvars64.bat` (for the
  C headers and link libraries), and the Swift runtime directory on `PATH` for
  running the built program.
* Swift 6.4's SDK module maps expect a *current* Windows SDK: they name SDK
  10.0.26100 and reference `stdnoreturn.h`, which VS2019's SDK 10.0.19041 does
  not contain. On this machine the single missing module was removed from
  `…\Windows.sdk\usr\share\ucrt.modulemap` (a backup is kept beside it as
  `ucrt.modulemap.orig`). Installing Visual Studio 2022 Build Tools with the C++
  workload is the proper fix and makes that edit unnecessary:
  `winget install Microsoft.VisualStudio.2022.BuildTools --override "--quiet
  --wait --add Microsoft.VisualStudio.Workload.VCTools --includeRecommended"`
  (needs an elevated shell).
* The `ocaml` entry builds with `opam exec -- ocamlopt`, which works without
  sourcing the switch environment first (the opam switch is self-contained, so
  no extra `env` entry is needed). `ocamlopt` has no output directory option and
  drops `connect_four.cmi`/`.cmx`/`.o` next to the source, so those extensions
  are in the OCaml section of `.gitignore`.
* Fortran builds with `gfortran` from the same MinGW-w64 prefix the `assembly`
  entry uses, so `fortran` also selects it with `mingw64_env()`. The reference
  implementation works wholly on fixed-length `character` values, which is why
  the token is trimmed with a hand-written `cleaned()` (the same whitespace set
  as C's `isspace`) rather than `adjustl`/`trim` alone.
* The `php` entry has no build step. `php_env()` only prepends a PHP directory
  to `PATH`, because the Windows PHP releases are plain archives while the
  winget/choco packages install machine-wide (so they need an elevated shell).
  Here PHP was unpacked to `C:\tools\php` from the official
  `php-8.5.11-nts-Win32-vs17-x64.zip`; a `vs17` build needs the VS2015+ x64
  runtime installed.
* PHP note that cost a debug cycle: `EMPTY` is a reserved construct (`empty()`),
  so the board's blank-cell constant is called `EMPTY_CELL`.
* The `haskell` entry builds with `ghc -outputdir tests/build/haskell`, which
  keeps `connect_four.hi`/`.o` out of the source directory, and uses only
  `base`, so no cabal/stack package setup is involved. The program sets
  `stdout` to `NoBuffering` so prompts precede reads, and detects end of input
  with `isEOFError` from the caught `getLine`.
* The `dart` entry AOT-compiles with `dart compile exe`, so tests launch a
  standalone binary instead of the JIT VM (`dart run` would re-resolve the
  package each time and start far slower). Dart writes `\n` rather than `CRLF`
  on Windows — the runner normalises line endings. `stdin.readLineSync()`
  returns `null` at end of input and strips the `\r` of a CRLF pair, and the
  standard `stdout` sink flushes the prompt (which has no trailing newline)
  before the read, so no explicit `flush()` is required.
* The `powershell` entry runs under Windows PowerShell 5.1, which ships with
  Windows (`-NoProfile -ExecutionPolicy Bypass -File`) — nothing to install; on
  Linux/macOS the same script runs under `pwsh`. It writes through
  `[Console]::Out.Write` rather than `Write-Output`/`Write-Host` so the
  newline-free prompt reaches the pipe before the read, and
  `[Console]::In.ReadLine()` returns `$null` at end of input while stripping a
  trailing `\r`. The board is a flat 42-cell array, which sidesteps
  PowerShell's array-unrolling when a function returns a nested array.
* The trap that cost a debug cycle here: **PowerShell variable names are
  case-insensitive**, so a loop-local `$row`/`$column` in a function whose
  parameters are `-Row`/`-Column` is *the same variable* — the parameter gets
  overwritten each iteration, so the win scan advanced its offsets cumulatively
  (columns 0, 1, 3, 6) and never found a run. The locals are named
  `$targetRow`/`$targetColumn` instead. Related: `-eq`/`-ne` are case-*insensitive*
  for strings, so the board comparisons use the case-sensitive `-ceq`/`-cne`.
* The `bash` entry needs `bash_tool()` in the runner: Windows ships no bash and
  neither Git for Windows nor MSYS2 puts it on `PATH`, so the interpreter is
  resolved at `C:\Program Files\Git\{,usr\bin\}bash.exe` and then
  `C:\msys64\usr\bin\bash.exe` (elsewhere it is simply `bash`). It runs with
  `--noprofile --norc` for startup speed and isolation, and both builds accept
  the plain Windows script path with either slash style.
* Bash notes: `IFS= read -r line` (the `-r` matters, since plain `read` eats
  backslashes), and the `\r` of a CRLF line is removed by the hand-rolled
  `[[:space:]]` trim, which is the same set C's `isspace` covers. `printf` is a
  builtin writing straight to fd 1, so the prompt appears before the read.
  Two structural choices follow from the language: bash functions cannot return
  strings and capturing a prompt-printing function with `$(...)` would swallow
  its output, so `ask_column` prints through and hands its answer back in the
  global `$CHOSEN_COLUMN`, while only the pure helpers (`trim`, `parse_value`,
  `lowest_empty_row`) are called via `$(...)`. The board is a flat global array
  (`declare -a BOARD`) because bash cannot pass arrays by value.
* The `ada` entry compiles with GNAT from MSYS2's `mingw-w64-x86_64-gcc-ada`
  package (`pacman -S`), which installs into `C:\msys64\mingw64\bin` — not on
  the default `PATH`, hence `gnat_tool()`/`gnat_env()`. Two wrinkles: that
  directory must exist *before* `gnatmake -D` runs (so `_gnat_object_dir()`
  creates `tests/build/ada`; every object then lands there and the source
  directory stays clean), and Alire's `alr` is deliberately not used, since it
  wants to install its own copy of msys2 and prompts interactively.
* Ada notes: `Get_Line` (through `Ada.Text_IO.Unbounded_IO`, a GNAT child unit,
  so a line can be any length) already drops the CR of a CRLF pair and raises
  `End_Error` at end of input, and the hand-rolled trim covers the same six
  characters C's `isspace` does. Ada buffers `Standard_Output` when it is not a
  terminal, so each prompt is followed by `Flush` before the read — without it
  the interactive check would see no output before input. `'Image` is avoided
  because it pads non-negative numbers with a leading space (the `Image_Of`
  helper strips it), and the parse loop guards with
  `Value > (Max_Value - Digit) / 10`, since GNAT enables overflow checks and an
  unguarded multiply would raise instead of saturating like `strtol`. The Ada
  runtime links statically, so the built program needs no `PATH` entry to run.
* The `pascal` entry uses Free Pascal, installed per-user with
  `scoop install freepascal` — Scoop's shim puts `fpc` on `PATH`, so no
  resolver dance is needed (`fpc_tool()` still checks the stock installer
  locations as a fallback). Scoop's manifest ships the **i386** build, which is
  fine: the 32-bit executable runs on x64 Windows.
* Pascal notes: `and then` is **not** available in `{$MODE OBJFPC}`, and FPC's
  `and` is complete-evaluation by default, so the trim loops are written as
  `while ... do begin if not ... then Break; ... end` rather than relying on
  short-circuit evaluation (which would index past the end of an empty string).
  `Readln` leaves the `\r` of a CRLF pair for the trim to remove (it covers the
  same six characters as C's `isspace`), `Eof(Input)` is the end-of-input test,
  and a bare `Writeln` produces the blank line before a warning or the win
  message. Ada's buffering caution applies here too: `Flush(Output)` after each
  prompt is what makes the interactive check pass. Finally, `fpc` will not
  create its `-FU`/`-FE` directories, so `_fpc_output_dir()` makes
  `tests/build/pascal` first — objects and the executable land there and the
  source directory stays clean.
* The `v` entry uses V's official Windows zip (the release asset is
  `v_windows.zip`, *not* `v_win.zip`), unpacked to `C:\tools\v`; `v_tool()`
  resolves it because `v.exe` is not on `PATH`. The archive nests everything one
  level down (`v/…`), so the contents are moved up a level, and it bundles
  `tcc` under `thirdparty/tcc` — V's default C backend, so no external compiler
  is needed.
* V notes: `os.input_opt(prompt)` is exactly the right primitive here — it
  prints the prompt verbatim, calls `flush()` immediately, strips a trailing
  `\r\n`, and *distinguishes an empty line from end of input* (`''` vs `none`),
  because it length-checks the raw line before trimming. The whole-number test
  indexes bytes and compares them against u8 rune literals for `'0'` and `'9'`,
  matching C's `isdigit` over bytes rather than over decoded runes, and the
  parse saturates at `i64` max like the other implementations. `v -o <exe> <src>`
  leaves the source directory untouched (V keeps its intermediates in its own
  cache), and a full build takes well under a second since tcc is the backend.
* The `julia` entry is a script language with no build step: `julia_tool()`
  resolves the interpreter (Scoop's shim, so it is on `PATH` here), and the run
  passes `--startup-file=no --color=no` for a faster, isolated start.
* Julia notes: `print` needs an explicit `flush(stdout)` before the read — the
  same buffering caution as Ada and Pascal. End of input is detected with
  `eof(stdin)` *before* calling `readline()`, because `readline()` returns `""`
  both at EOF and for an empty line. `readline()` does strip the `\r` of a CRLF
  pair (the probe showed the raw bytes coming back without `0x0D`), and the
  whole-number test walks `codeunits`, so it matches C's `isdigit` over bytes
  rather than over decoded characters. The board is a `Matrix{Char}`, and
  Julia's 1-based indexing lines up with the on-screen column numbers, so the
  parsed value is used as the column index without adjustment.
* The `r` entry is a script language with no build step: `r_tool()` resolves
  `Rscript`, and the run passes `--vanilla` (no site/user files, no saved
  workspace), which also keeps startup fast and stderr clean.
* R notes, hard-won one first: reading stdin **incrementally** in a script needs
  a connection opened *once* — `input_stream <- file("stdin", "r")` at the top,
  then `readLines(input_stream, n = 1)`. Both `readLines("stdin", n = 1)` and
  `scan("stdin", nlines = 1)` reopen the pseudo-file on every call and throw
  away R's buffered read, so the *second* call reports EOF (the game ended after
  one move); `stdin()` behaves the same way, and `readline()` does not read
  piped stdin under `Rscript` at all. `readLines` returns `character(0)` at end
  of input, which is how EOF is told apart from an empty line, and the read is
  wrapped in `suppressWarnings` so a closing-connection warning cannot reach
  stderr. `readLines` also strips the `\r` of a CRLF pair, `flush(stdout())`
  after each prompt keeps the interactive check happy, and the trim uses the
  POSIX `[[:space:]]` class — exactly the six characters C's `isspace` covers.
  Like Julia, R is 1-based, so the parsed column value is used as the board
  index directly.
* The `lisp` entry is SBCL used as a script language: `sbcl --script <file>`
  (which implies `--noinform --no-userinit --no-sysinit --disable-debugger`), so
  there is no build step and no REPL banner. Scoop unpacks SBCL's MSI, avoiding
  the installer's elevation, and `lisp_env()` supplies `SBCL_HOME` — SBCL finds
  `sbcl.core` that way, Scoop only sets it for new shells, and a shell already
  running when SBCL was installed will not have it.
* Lisp notes: `read-line` is called with an explicit `nil` eof-value (rather than
  the default `:eof`), which turns the end-of-input test into a plain `null`
  check and is how EOF is told apart from an empty line. Unlike Julia and R,
  SBCL **keeps the `\r`** of a CRLF pair (the probe showed raw codes
  `(32 32 52 50 32 13)`), so the trim must remove it; it uses a char bag built
  from the codes `(9 10 11 12 13 32)` — exactly C's `isspace` set, and built with
  `code-char` because vertical tab has no standard character name. `finish-output`
  after each prompt is what makes the interactive check pass, and the
  whole-number test compares with `char<=` against `#\0`/`#\9` instead of relying
  on `digit-char-p`. Integers are bignums, so unlike every other implementation
  no saturation guard is needed: an absurd token simply fails the range check and
  is echoed back.
* The `elm` entry is the most involved integration here, because **Elm cannot
  read stdin on its own**: a console Elm program has to be a `Platform.worker`
  with ports, driven by a JavaScript host. `_elm_project()` therefore assembles a
  throwaway project under `tests/build/elm/` from the single source file plus a
  host template — it writes `elm.json`, writes `host.js`, and copies
  `languages/elm/connect_four.elm` in as `src/ConnectFour.elm`. Three Elm rules
  force that dance: a module's file name must match its module name (hence the
  rename on copy), source files must live inside the project directory, and
  `elm.json` must declare `elm/json` ("It helps me handle flags and ports") even
  though `elm/core` is the only direct dependency. The manifest's `elm-version`
  is read from `elm --version` rather than hard-coded, since a mismatch is
  rejected outright. Nothing is generated inside `languages/`.
* The generated host bridges `process.stdin` to the `fromHost` port one line at
  a time (`readline` with `crlfDelay: Infinity`, which also strips the `\r`),
  maps stdin close to a `Nothing` message so Elm can tell EOF from an empty
  line, and writes whatever `toHost` sends with `process.stdout.write` — adding
  no newlines of its own. Because Elm delivers port messages asynchronously and
  the interactive check keeps stdin open, ending the game by relying on stdin
  closing was not enough: a second port (`quitToHost`) tells the host to close
  the interface and call `process.exit(0)` from inside a `stdout.write`
  callback, so buffered output is flushed before exiting.
* Build with `--optimize`: besides being faster it suppresses the runtime's
  dev-mode "Compiled in DEV mode" notice, which would otherwise land on stderr.
  The whole-number test compares characters against `'0'`/`'9'`, the parse
  saturates at `maxValue` (Elm's `Int` is a JS number, so the guard keeps it
  exact), and the trim walks an explicit six-character whitespace list.
* Record the exact install command you used in the README install notes so
  the next contributor can reproduce it.

## Cross-platform gotchas

* **Read stdin line-by-line** (one line per prompt), never all at once, and
  **flush stdout** before reading. The suite's interactive I/O check fails any
  implementation that waits for end of input, or that buffers its output
  instead of showing the prompt immediately — both break interactive play.
* **Flush stdout** after printing a prompt, before reading input.
* **Never read all of stdin up front** (e.g. `fs.readFileSync(0)` or
  `read_to_string`); that returns immediately at a terminal and breaks play.
* **Line endings** differ: C in text mode and Python on Windows translate
  `\n` to `\r\n`. The test runner normalizes CRLF/LF, but do not emit
  trailing whitespace at the end of a line.
* Print the prompt first, read a whole line, strip surrounding whitespace.
  A token is a whole number only if it is an optional `+`/`-` followed by
  ASCII digits (reject unicode digits, `3.5`, `0x10`, etc.).
* On invalid input, print the warning on its own line and **reprint the full
  prompt** before reading again.
* After each valid move print a newline, then the board, then the next
  prompt.
* A column is `1`-based on screen (`1`-`7`) but usually `0`-based
  internally.
* Empty cells are `.`, the bottom row is printed last.
* The winner message is `Player X wins!` / `Player O wins!`; a full board
  with no four is `It's a tie!`; a closed stdin is `Input closed. Goodbye.`

## Showcase dashboard

The dashboard is a Vue 3 + TypeScript app (`src/`) built by Vite, and it lives in
the same repository as the implementations it shows. `public/dashboard-data.js`
is **generated** by `python tools/generate_dashboard.py` (run through
`npm run data`, which finds Python for you); never hand-edit it and never commit
it — CI regenerates it on every deploy. To add display metadata (name, Prism
language, category) for a new language, extend `LANGUAGE_INFO` in the generator.

```
index.html             Vite entry: head metadata, the data <script>, mount point
src/main.ts            mounts App.vue, clears the 404 hop counter, sets up theme/Prism
src/App.vue            layout + the outside-click/Escape listeners
src/components/        AppSidebar, FacetDropdown, ItemList, DetailHeader,
                       SourceView, ConsoleView, PreviewView, EmptyState
src/store/data.ts      reads window.CONNECT_FOUR_DATA and answers lookups over it
src/store/session.ts   the reactive selection, the URL router and the three facets
src/store/theme.ts     the dark/light toggle and the Prism stylesheet swap
src/prism.ts           grammar-on-demand highlighting (string API - see below)
src/types.ts           the shape of the generated payload
src/styles/app.css     palette tokens + the Tailwind entry + helper classes
```

The data is loaded with a classic `<script>` tag from `public/`, so it runs before
the app module, needs no `fetch`/CORS and stays out of the app bundle. Both lists
share one shape, so everything downstream reads `allItems()`, and a language needs
no extra step: the id in `languages/<id>/` becomes its path automatically.

Every implementation is addressable at `/<language-id>` (`/ada`, `/c`,
`/objectivec`), with `?tab=output&scenario=<id>` for the console view. The site
root opens the C# implementation — the fallback id is `DEFAULT_LANG_ID` in
`src/store/data.ts`, and `defaultLangId()` degrades to the first language in the
data if that id is absent — and the sidebar renders real `<a href>` links, so the
router in `src/store/session.ts` keeps the address in step with the selection
(History API `pushState`/`replaceState` plus `popstate`, so back/forward work and
ctrl/middle clicks open a new tab). Two shapes are read on load, path first then
query: `/ada` (a tolerated `/ada/output` too) and `?lang=`/`?tab=`/`?scenario=`,
which is the shape `404.html` forwards. `canWritePath` probes whether the document
accepts path writes once at load (restoring the temporary URL in the same tick,
before the sidebar renders) and everything uses the query form when it is false,
with the refused-write fallback in `syncUrl` as a backstop. Never drop that
fallback: it is what keeps older links and the `404.html` shim working. The app is
an ES module bundle now, so a `file://` document cannot run it at all — `npm
start`, `npm run preview` and `tools/serve.py` are the ways to look at it.

The sidebar header also carries a `Languages` / `Frameworks` pill that swaps the
list's source. `state.mode` picks between `data.languages()` and
`data.frameworks()` through `modeItems`; the search, the three facets and the
sidebar all render from that one accessor, so a new browse mode needs no
per-component change. Frameworks are discovered from `frameworks/<id>/` plus the
generator's `FRAMEWORK_INFO` and share a language's shape, with extra fields:
`folder` (the GitHub link target), `note`/`linkText` (the banner above the code,
whose `{link}` becomes an anchor to the whole project, rendered from
`noteSegments`), `stack`/`languages` for the two Frameworks-only facets, and
`preview` for a browser-only implementation. The mode is deliberately *not*
written to the address — the router only ever names an item — and switching modes
resets the search and every facet to keep the two lists independent. Because
`knownLang`/`currentItem` read `allItems()` (both lists), opening a framework's
`/<id>` reveals the Frameworks list on load, and `setMode` selects an item so the
code panel always matches the visible list. That selection goes through
`applySelection()` rather than `selectLanguage()`, because the two have different
drawer behaviour on mobile: a tap on a list row ends the interaction, so it closes
the drawer, while the mode pill is *how* you reach the other list, so the sidebar
stays open and shows it. `selectLanguage` is `applySelection` plus that close, so
keep the close out of the shared helper.

The sidebar's filters are three labelled dropdowns (`categoryOptions`,
`stackOptions`, `languageOptions`): `Category` (both modes), and — only in
Frameworks mode — `Stack` (Frontend / Backend / Full stack, from the generator's
`FRAMEWORK_STACKS`; the menu lists just the values present) and `Language` (from
`FRAMEWORK_LANGUAGES`, unioned across every framework, ordered most-used first,
with a count per option).

They are custom dropdowns rather than native `<select>`s, because an OS-drawn
popup cannot be height-capped: `FacetDropdown.vue` renders one, `state.openMenu`
keeps a single menu open, and the panel scrolls after ~8 rows (`.menu-scroll`,
`max-h-56`), closing on an outside click or Escape (the document listeners in
`App.vue`). `visibleItems` applies all three facets.

Stacks read as short badges: `STACK_TAG` maps Frontend/Backend/Full stack onto
FE/BE/FS for the sidebar row, while `STACK_LABEL` spells them out ("Frontend
(FE)") for the dropdown. Languages read as blue file-extension tags, shown on a
framework's sidebar row and under the GitHub link in the detail panel:
`languageTag()` looks a name up in `DATA.languageExtensions` (the generator's
`LANGUAGE_EXTENSIONS`) to get ".ts"/".cs"/".py" and `.lang-tag` styles the pill,
each tag carrying a `title` with the full language name. The filter dropdowns
stay plain text on purpose.

Three implementation notes worth keeping:

* **The height chain is explicit, and the app is a fragment.** `body` declares
  `height: 100vh/100dvh` and `#app` declares `height: 100%` in
  `src/styles/app.css`, and `App.vue` renders its three children (scrim, sidebar,
  main column) as siblings rather than inside a wrapper. A percentage height
  inside an auto-height box resolves to `auto`, so wrapping the app in one more
  div - or dropping the `#app` rule - lets the sidebar grow to the full height of
  its list (~5000px of languages) instead of scrolling, and `body`'s
  `overflow: hidden` then hides the rest: the page cannot scroll either. The
  original page put these classes on `<body>` itself; `#app` is the mount point
  that has to take its place.
* **A control the header cannot fit gets its own row, never a squeeze.** The
  capture picker is `flex w-full sm:w-auto` inside a `flex-wrap` group, so below
  `sm` it takes a row instead of shrinking the tab bar (which is what the old
  page did by stripping the element's `hidden` class from JavaScript, wrapping
  the buttons inside their own bar and squeezing the theme button to 25px). The
  same measurement rules apply to the sidebar: its list must keep a scroll range
  at every width, and every row must stay reachable.
* **Prism renders a string, not the DOM.** `src/prism.ts` resolves a grammar (via
  the autoloader's `loadLanguages`, from the same CDN the page links) and returns
  `Prism.highlight(...)`, which `SourceView.vue` renders with `v-html`. Never call
  `highlightElement()` on an element Vue owns: the next patch would wipe the
  highlight and the line-number gutter would stop lining up. A grammar the CDN
  does not have (or `language-none`, used for the console capture) leaves escaped
  plain text, exactly as before the rewrite.
* **The code panel's two columns** must keep **identical top insets** (`pt-2` on
  the gutter, `padding-top: 0.5rem` in the `pre.cf-code` override) and the value
  must stay **under one line-height** (13px × 1.625 = 21.125px). A full line of
  head room reads as a stray blank first row above line 1; the bottom inset stays
  at `pb-5` / `1.25rem`.

The header also links each
implementation to its own folder on GitHub, labelled `View languages/<id> on
GitHub` behind a GitHub mark (its title and target are
`<repository>/tree/<branch>/<source folder>`), built from
`meta.repository`/`meta.branch` — the generator fills those from the git remote,
else `GITHUB_REPOSITORY`, else its committed default, so no page-side list of
URLs to maintain. The sidebar's header carries the same mark beside the home
mark (pattygcoding.com), pointing at the repository *root* instead of a folder:
`repoHomeUrl()` in `src/store/data.ts` reads the same `meta.repository`, with the
committed default only as the fallback for a checkout whose data is not
generated yet, so the two links can never disagree about the project.

GitHub Pages has no rewrite rules, so `public/404.html` is part of the routing
contract: it is served for any unknown path with the address bar untouched, and
rebuilds the request as `index.html?lang=<id>` — forwarding any other query the
link carried, so `scenario` survives — while climbing one directory for anything
that is not a bare slug (with a hop cap and a never-re-request-the-same-address
check) so a typo can never redirect in circles. The dashboard then rewrites the
bar back to `/<lang>` (and `main.ts` clears the hop counter). Keep the two in
step, and keep the file tracked in git: it is the only reason refreshing a pretty
path such as `/csharp` works on Pages. `tools/serve.py` serves the built `dist/`
with that same fallback, which is why it — not `python -m http.server` — is the
documented way to check what is deployed: a bare file server answers `/csharp`
with its own 404 page, so a refresh looks broken even though the deployed site is
fine. The dev server (`npm start`) reaches the same place by rewriting unknown
paths to `index.html`, and `npm run preview` serves the built files with no
fallback at all.

The visual design deliberately mirrors the author's portfolio: a navy canvas
(`#05070c` dark / `#f4f6f5` light), a mint accent, Inter for text and JetBrains
Mono for the small uppercase tracking-wide labels.

The palette lives in CSS variables declared in `src/styles/app.css` (`:root` =
dark, `html[data-theme="light"]` = light), and the Tailwind theme in
`tailwind.config.js` resolves to them (`ink.950: "rgb(var(--ink-950) /
<alpha-value>)"`, plus the semantic
`fg`/`fg-strong`/`fg-soft`/`fg-muted`/`fg-dim`, `gutter`, `hint`, `console`,
`line` and `accent` colours). The `.micro` label helper is declared there too.
Keep new markup on those tokens — never a raw hex value or a stock Tailwind grey.
Tailwind is pinned at 3.4, the major the page used to load from the Play CDN, so
the stylesheet is built now without the design moving. The scanner is not a
runtime: a class list assembled by string concatenation still has to appear as a
complete literal somewhere in `src/`, so keep the branches of a dynamic `:class`
spelled out.

* `accent` is for text, borders and rings; `mint.400` is the pale *fill* used
  with `text-on-accent`. They differ in light mode (the accent darkens so it
  stays legible on white), so a filled pill and an accent label are not the same
  class.
* `line/5`, `line/10`, `line/20` replace the old `white/N` borders and hovers.
* The header's sun/moon button calls `toggleTheme()` (`src/store/theme.ts`),
  which flips `data-theme` on `<html>`, remembers the choice in
  `localStorage["cf-theme"]`, and parks the unused Prism stylesheet behind
  `media="not all"` (both the `prism-tomorrow` and default light themes are
  linked). The script in `<head>` applies the stored/`prefers-color-scheme` theme
  before first paint, so never re-introduce a flash by setting it later.

## Commands

```sh
npm install                             # once, then either of the first two:
npm start                               # regenerate the data + dev server on :5173
npm run build                           # regenerate the data, type-check, write dist/
npm run preview                         # serve the built dist/ with Vite
npm run data                            # only regenerate public/dashboard-data.js
npm run typecheck                       # vue-tsc --noEmit
python tests/run_tests.py               # build everything and verify
python tests/run_tests.py --update      # regenerate tests/expected/ after a protocol change
python tools/generate_language_readmes.py  # regenerate every languages/<id>/README.md + banner.svg
python tools/serve.py                   # preview the built dist/ with Pages' 404.html fallback
gh api -X PUT repos/<owner>/<repo>/pages -f build_type=workflow  # once: publish from Actions
gh api -X PUT repos/<owner>/<repo>/pages -f cname=<domain>       # once: attach the custom domain
```

`npm run build` is exactly what CI runs (`.github/workflows/deploy.yml`), so a
green local build means the deployment will build too. `python -m http.server` is
*not* a substitute for `tools/serve.py`: refreshing any of the dashboard's pretty
paths (`/csharp`) would answer with its own 404 page, and it would serve the
sources rather than the built site.
